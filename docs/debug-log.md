# 调试日志与导航系统理解

本项目参加导航赛道，任务是自主完成有序 8 字路线、处理障碍并回到停车位。以下记录从搭建仿真到定位、控制、通信和障碍处理的调试过程，实验数据均来自本机仿真。

## 系统理解

Point-LIO 根据点云与 IMU 估计连续运动，small_gicp 负责与先验地图对齐。前者提供连续性，后者约束累计漂移，两者还需要正确的时间戳和 TF 才能被导航使用。TF 将地图、里程计、底盘和雷达的关系提供给任务与控制节点；二维代价地图用于表示可通行区域和实时障碍。加载先验地图、定位输出正确、控制器能跟踪路径是三个需要分别验证的条件。

本项目的解析先验来自仿真场景几何；传感器点云汇总成 PCD 的实验仍依赖该先验对齐，不能据此称为无先验建图。

任务层保存绕下桩、绕上桩和返回的顺序，控制器执行当前分段路径，最终速度保护再检查输入时效、危险区和速度限幅。绕行还要保留绕桩方向、整体绕数以及实际入场路径，不能只检查最后是否到达停车位。

排查时沿“传感器 → 位姿/TF → 代价地图 → 当前路径 → 最终速度 → 底盘实际运动”逐层确认。上游公开场景的详细关系见[导航数据流](architecture/navigation-dataflow.md)，本赛任务见[仿真说明](simulation/arena-mission.md)。

## 2026-09-27：仿真未使用 GPU

**现象与排查。** RViz 和 Gazebo 可以打开，但 OpenGL 渲染器为 `llvmpipe`。容器已映射 `/dev/dxg` 和 `/usr/lib/wsl/lib`，仍缺少 `/usr/lib/wsl/drivers`；D3D12 能加载接口库，却找不到 Windows 显卡用户态驱动。

**处理与效果。** 完整只读挂载 `/usr/lib/wsl` 后，NVIDIA 和 Intel 的 OpenGL 探测都报告 `Accelerated: yes`。NVIDIA 模式又在 Fortress 的 OGRE2 纹理复制路径遇到 `UnimplementedException`，改用内置 OGRE 后，实际 RViz、Gazebo 服务端和 GUI 均加载 NVIDIA 驱动，场景、雷达、IMU 及重复启停正常。

**理解。** 设备映射、驱动加载和渲染器兼容性需要分别检查。这里的 GPU 加速用于图形和仿真传感器，Point-LIO、small_gicp 与导航计算仍在 CPU 上运行；选择 OGRE 满足了运行需求，没有修复 OGRE2 本身。配置见 [GPU 说明](deployment/gpu.md)。

## 2026-09-27 至 09-28：跨容器能发现话题，却收不到数据

**现象与排查。** 仿真和导航分开运行时，ROS 能列出话题，同一容器内也能收到消息，另一容器却没有数据。容器使用主机网络，但 IPC 隔离；Fast DDS 将参与者识别为同主机并选择共享内存，实际共享内存不可达。尝试 UDP 配置未解决该次故障。

**处理与效果。** 统一使用 `--network host --ipc host`，独立容器之间收到实际点云和 IMU，后续定位、到点与取消流程才能继续。

**理解。** DDS 发现与数据传输是不同环节，`ros2 topic list` 不能证明数据可用。诊断应比较同进程、同容器和跨容器的真实订阅结果。

## 2026-09-28：RViz 正常运行，退出时崩溃

**现象与排查。** 导航到点可以完成，关闭 RViz 时却在 `rclcpp::CallbackGroup` 析构的虚函数调用处崩溃。升级 rclcpp 后仍可复现。GDB 中的目标地址与退出前的进程映射对照，指向已经卸载的 `libnav2_rviz_plugins.so`。

**处理与效果。** 仅对独立 RViz 进程预加载该插件，使其代码在回调控制块销毁期间保持可用。同时先关闭 RViz 请求端，再在仿真时钟仍运行时清理 Nav2 生命周期节点，最后关闭 Gazebo 和其他 ROS 节点。两轮完整导航和两轮待机退出均正常结束。

**理解。** 启动和导航成功都不能证明资源释放顺序正确。该处理是针对当前 Humble 插件卸载顺序的规避，不能视作所有版本的通用修复；还应检查子进程退出状态，不能只看 launch 返回码。

## 2026-09-28：雷达点内时间与 Point-LIO 参数不一致

**现象与排查。** 将传感器链接入双桩场景时，发现上游转换器生成秒制点内时间，既有 Point-LIO 配置却按微秒解释；附加的 0.1 秒扫描偏移也与 Gazebo 整帧瞬时采样不一致。直接让所有点使用同一时刻的尝试出现定位失稳。

**处理与效果。** 自有 `lidar_adapter` 明确输出秒制时间，Point-LIO 设置 `timestamp_unit=0`；采用不超过 100 ns 的微小排序偏移近似瞬时扫描。抽样核对字节字段、点值和时间单调性，再运行传感器定位基础运动及连续五圈任务，实际回位误差为 1.7–5.0 cm。

**理解。** 点云能被订阅不代表算法输入语义正确。字段类型、单位、扫描起止时刻和点内顺序都影响融合；上述适配只对应仿真瞬时扫描，不代表真实 MID-360 的扫描时序或运动去畸变已经验证。

## 2026-09-28：生命周期请求偶发收不到响应

**现象与排查。** 启动和退出时偶发服务响应丢失，不能仅凭服务可发现判断请求完成。排查到 Fast DDS 服务回复 writer 的读者发现等待默认为 100 ms，存在响应发送与发现建立的竞争。

**处理与效果。** 将项目服务回复 writer 的等待设为 5 秒，使用原生 DataWriter API 确认实际值为 5,000,000,000 ns。启动时先确认时钟、里程计和服务响应，激活后再查询生命周期状态；重新运行启动与退出流程正常。普通话题 QoS 保持不变。

**理解。** 发现服务、收到回复和节点进入 `active` 是三个不同条件。延长发现等待用于解决回复竞争，不等于给所有数据统一增加五秒延迟。

## 2026-09-28：闭环路径与交叉点进度

**问题与原因。** 圆形闭环起终点相同，控制器可能提前判断到达终点；8 字交叉点重复经过，单纯选择全局最近路径点可能匹配到另一个阶段。另有 action 成功先于新 TF 到达，以及短段进度取整造成的误报。

**处理与效果。** 将弧线拆成最多 90° 的有序分段，每段使用连续投影与单调进度。action 成功后最多等待 0.5 秒取得最新位姿，再复核终点和进度；运行中拒绝复位，复位只清任务状态。相同任务分别在理想定位和传感器定位下连续完成五圈，独立真值轨迹确认下桩约 +2π、上桩约 −2π。

**理解。** 空间位置不能代替任务状态。交叉点的同一坐标可能对应不同访问阶段；停车回位、完整绕桩和规定顺序需要分别检查。

## 2026-09-30：串口收帧与底盘运动链路

**问题与处理。** 比赛发送帧为固定 19 字节、12 字节数据段，没有 `cmd_id`；接收字节流可能半帧、连帧或夹杂噪声，不能把一次读取等同于一帧。独立实现 CRC8/CRC16、长度校验、有限数检查和逐字节重同步，按 10 ms 稳态周期发送一条完整帧。

**效果。** 将运动链改为 `motion_guard → serial_bridge → 伪终端 → sim_mcu → Gazebo`，Gazebo 只消费模拟下位机输出。完整传感器任务中累计发送 8,700 帧，模拟下位机观测到的序号缺口与错误字节均为零，最大发送间隔为 11.7 ms。双方计数来自不同采样时刻，计数差不直接作为丢帧依据。

**理解。** 编解码正确与底盘确实经过通信链是两个问题。伪终端可以检查字节流、序号回绕和控制路径，但不能替代真实 UART 电气时序；软件状态也不能替代实际运动观测。

## 2026-09-30：动态障碍影响定位与停车

**现象与排查。** 首轮下瓣插入障碍时，估计位置相对真值出现约 0.47 m 的 y 向偏移，临时车体接触箱体。动态物体影响重定位，仅依赖地图坐标下的路径碰撞判断不足以保护车体。另一次运行中，控制器先依据内部代价地图中止 action，任务节点随后才收到对外地图。

**处理与效果。** 增加原始雷达在车体坐标下的独立近距保护，检测后先关闭运动使能，再取消当前 action。对控制器中止短暂等待障碍证据，确认阻断则保留当前分段，无证据则进入故障。近距保护又暴露无回波零点和固定桩误触发，分别过滤无效点、按静态净距收紧保护范围，并加入稳定启动判断。

**复验与理解。** 驶入、下瓣、上瓣和交叉点四处行进中插障碍均停车，移除后从同一分段恢复并完成路线，实际回位误差为 1.4–3.5 cm。定位、地图和控制器的时序并不完全一致，独立近距保护可以减少对全局定位及地图更新的依赖；障碍停车后也应保存阶段，避免恢复时漏绕。

## 2026-10-12 至 10-13：点云传输丢帧

**现象。** 导航侧点云频率偏低，GUI 使用 GPU 后仍然丢帧。

**排查。** 同一 12 秒墙钟窗口内，Gazebo 原生发布 240 帧，ROS 只收到 35 帧。单帧为 1,024,000 字节，旧共享内存段为 512 KiB；生成频率正常，问题落在传输环节。

**处理与验证。** 配置 32 MiB 共享内存段、2 MiB 最大消息，自定义 UDP 仍限定回环地址。两轮对照都恢复为发布 240 帧、接收 240 帧，普通话题 QoS 和定位失效门限不变。

**得到的理解。** 渲染、传感器生成和 DDS 传输需要分别计数。这与早期 IPC 隔离不同，共享内存可达后仍需检查消息尺寸和缓冲容量。按仿真消息时间戳得到的 20 Hz，也不能单独证明墙钟实时性能或 NUC 性能。

## 2026-10-12 至 10-13：初始化与安装变换

**现象。** 赛方模型落地后的早期 Point-LIO 输出出现约 −90° 横滚和平面偏移；安装变换尚未取得时也出现错误点云。

**排查。** 初始离地过程产生近零加速度，过早初始化把噪声当作重力方向；另一路问题来自 LOAM 安装矩阵初始化与静态 TF 到达顺序。

**处理与验证。** 仿真适配器等待 IMU 连续稳定 0.5 秒，再送入扫描。安装变换显式初始化，取得有效 TF 前不转换点云。静止位姿、已知点坐标变换、真实 ROS 节点回归及完整传感器路线通过。

**得到的理解。** 模型显示正确只证明几何资源加载，导航还依赖传感器单位、重力初始化、时间语义和坐标变换。传感器模式使用估计位姿，Gazebo 真值只用于独立验收；理想定位的成功不能代替传感器定位验证。实车需要自己的静止初始化和外参标定。

## 2026-10-12 至 10-13：消息同步与退出

**现象。** 里程计被点云配对额外延迟，大消息转换过程中接收退出信号也可能引发异常。

**处理与验证。** 底盘里程计和 TF 独立跟随传感器里程计发布，保留输入时间戳；点云同步只服务扫描转换。五个自有 ROS 节点共用退出入口，信号只设置停止标志，当前回调结束后再释放 executor、节点和上下文。无点云仍输出里程计、SIGINT/SIGTERM 大消息转换与清理均有回归验证。

**得到的理解。** 不同输出应依据各自的数据依赖决定是否同步；重新标记时间会掩盖真实延迟。进程退出还要考虑回调、消息转换和资源销毁的先后顺序。

## 2026-10-12 至 10-13：绕行后的原路返回

**现象。** 入口绕行后，使用原始返回段会走到障碍另一侧。

**原因。** 返回路径仍连接原始入口，没有采用实际入场衔接点。

**处理与验证。** 持续阻断后使用受原始路线走廊、绕桩方向和绕数约束的 A* 绕行。保存实际入场路径，末尾下瓣接回该入口，再逆序返回。独立真值轨迹审计检查四处绕行，返回偏差为 0.0374–0.0803 m，同时保持下桩逆时针、上桩顺时针及有序阶段。

**得到的理解。** 路径修改必须兑现整个任务的约束。完成绕行、完成一圈和沿原路回位需要分别检查。

## 2026-09-30、10-12 至 10-13：指令停车与物理停车

**现象。** 9 月 30 日模拟断链实验中，下位机保持约 0.180 m/s 的末帧，车辆继续前进约 0.061 m。10 月复测模拟串口物理断链后，上位机取消并发零速，模拟下位机仍保持末帧约 0.1721 m/s，观察窗口内移动约 0.0620 m；恢复链路后才停下。

**结论。** 没有下位机超时机制时，零速无法送达就不能依靠上位机实现物理停车。实验中模拟下位机保留末帧，未设置通信超时停车。

**得到的理解。** action 状态和 `cmd_vel` 只能说明软件层状态，实际运动与停车必须独立观测。断链、发送进程崩溃和断电后的停机需要下位机或硬件机制。
